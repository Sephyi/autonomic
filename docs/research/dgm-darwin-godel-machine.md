# Darwin Godel Machine & DGM-Hyperagent: Implementation-Grade Research Notes

Sources: arXiv:2505.22954v3 (Zhang et al., ICLR 2026) and arXiv:2603.19461v1 (Zhang et al., March 2026)

## Part 1: Darwin Godel Machine (DGM)

### 1.1 Core Concept

The DGM replaces the original Godel Machine's impractical requirement of *proving* self-modifications are beneficial with *empirical validation* on coding benchmarks. It combines Darwinian evolution (archive-based population search) with self-referential self-improvement (agents modify their own code repositories).

**Key assumption**: The system is a *coding agent* evaluated on *coding benchmarks*. Because self-modification is itself a coding task, improvements in coding ability directly translate to improvements in self-modification ability. This creates a virtuous cycle where getting better at the task also means getting better at improving yourself.

**Foundation models are frozen**. The LLM weights never change. All improvement happens in the scaffolding code: tools, prompts, workflows, and agent logic implemented in Python.

### 1.2 Architecture

#### Agent Representation

Each agent is a **Python code repository** powered by frozen pretrained foundation models (e.g., Claude 3.5 Sonnet). The repository contains:

- Tool definitions (bash execution, file editing, code search)
- Prompt templates and system instructions
- Workflow logic (how the agent orchestrates multi-step problem solving)
- Evaluation/validation code
- Any auxiliary utilities the agent has invented

Python is chosen because it is Turing-complete, giving the DGM the theoretical potential to build any computable machine.

#### The Archive

The archive is the central data structure. It is:

- **Initialized with exactly one seed agent** (a basic coding agent with minimal capabilities)
- **Append-only**: every generated agent variant is added, regardless of performance
- **Never pruned**: even poorly-performing agents are retained as potential stepping stones
- **Tree-structured**: each new agent records its parent, forming a branching evolutionary tree
- Agents that don't perform well but introduce novel features may enable breakthrough descendants later

The archive stores for each agent:

- The complete code repository (all source files)
- Benchmark evaluation scores (fitness)
- The number of children spawned from this agent
- Parent lineage information
- A description/summary of modifications made

### 1.3 The DGM Algorithm (Main Loop)

The DGM alternates between **self-modification** and **evaluation** phases:

```txt
Algorithm: Darwin Godel Machine
─────────────────────────────────
Input: Initial coding agent a_0, benchmark B
Initialize archive A = {a_0}
Evaluate a_0 on B, record score

Repeat for N iterations:
  1. SELECT parent agent from archive A
     - Selection balances performance and novelty
     - Higher-performing agents have higher selection probability
     - Agents with fewer existing children are preferred (novelty pressure)
     - Selection uses softmax over a composite score combining
       fitness and inverse child count

  2. SELF-MODIFY (generate child agent)
     a. The selected parent agent is given:
        - Its own complete codebase
        - Its past evaluation results and logs
        - A self-improve instruction (generated by analyzing
          performance gaps and the current codebase)
     b. The agent (using its FM) proposes code modifications
        as a diff/patch to its own repository
     c. The diff is applied to create a child agent with
        a new code repository

  3. EVALUATE child agent
     - Run child agent on a subset of benchmark B
     - Record the fraction of tasks solved correctly
     - This is the agent's fitness score

  4. ADD child to archive A
     - The child is always added (no filtering)
     - Record parent-child relationship
     - Record fitness score and modification description
```

### 1.4 Parent Selection Mechanism

Selection balances **exploitation** (picking high-performers) and **exploration** (picking agents with fewer children, encouraging diversity):

- Each agent in the archive has a **fitness score** (benchmark performance, e.g., % tasks solved)
- Each agent has a **child count** (number of times it has been selected as a parent)
- Selection probability is computed via **softmax** over a composite score that weights:
  - Higher benchmark performance (exploitation)
  - Fewer existing children (exploration/novelty pressure)
- This ensures even weaker agents occasionally get selected, preventing premature convergence
- The approach is inspired by quality-diversity algorithms and open-ended exploration research

### 1.5 Self-Modification Phase (Mutation)

When a parent agent is selected for self-modification:

1. **Context assembly**: The system compiles:
   - The agent's complete current codebase
   - Summaries of past evaluation performance (which tasks succeeded/failed)
   - Error logs from failed attempts
   - Notes on what has been tried before

2. **Instruction generation**: A fixed, handcrafted mechanism (this is a key limitation addressed by Hyperagents) analyzes the agent's past evaluation results and current codebase to generate a natural-language instruction directing where the agent should self-improve. This uses an LLM call with a fixed prompt template.

3. **Code generation**: The parent agent's FM generates a code diff (patch) that modifies the agent's own repository. The prompt includes the self-improve instruction, the codebase, and performance history.

4. **Application**: The diff is applied to create a new child agent with a modified codebase.

### 1.6 Types of Self-Modifications Discovered

The DGM autonomously discovered and implemented these improvements:

| Improvement | Description |
| --- | --- |
| Patch validation | Added a step to run project tests before declaring a fix complete |
| Granular file editing | Evolved from whole-file replacement to targeted string search-and-replace |
| Better file viewing | More fine-grained file viewing with context-aware navigation |
| Long-context window management | Improved handling of large codebases that exceed context limits |
| Multi-attempt generation | Generate multiple candidate solutions and rank/select the best one |
| Peer-review mechanism | Use a separate FM call to review and critique proposed patches |
| History-aware patching | Track what has been tried before (and why it failed) when making new changes |
| Code search tools | Added tools for searching across the codebase |
| Alternative model routing | Use different frontier models to evaluate and select best solutions |

### 1.7 Population Management Strategy

- **No pruning**: All agents are kept in the archive forever
- **No elitism gate**: Children are added regardless of whether they improve on the parent
- **Branching, not linear**: Multiple children can be spawned from any agent in the archive, creating a tree
- **Stepping stones preserved**: Temporarily worse agents that introduce novel features are kept, enabling future descendants to build on them
- **Parallelizable**: Multiple parent selections and mutations can run concurrently since agents are independent code repositories

### 1.8 Exploration vs. Exploitation Balance

| Mechanism | Effect |
| --- | --- |
| Softmax selection weighted by fitness | Exploitation: better agents selected more often |
| Inverse child count in selection | Exploration: under-explored agents get more chances |
| Archive is append-only (no pruning) | Exploration: preserves diverse stepping stones |
| No hard fitness threshold for archiving | Exploration: even regressions can be kept |
| Self-improve instruction analyzes failures | Exploitation: targeted improvement based on evidence |
| Open-ended branching from any archived agent | Exploration: parallel paths through search space |

**Key finding**: Without open-ended exploration (i.e., always building off the most recent/best agent only), performance plateaus. The archive-based branching is essential for continued improvement.

### 1.9 Concrete Benchmark Results

| Benchmark | Initial Score | Final Score | Notes |
| --- | --- | --- | --- |
| SWE-bench | 20.0% | 50.0% | Real-world GitHub issues with unit test verification |
| Polyglot | 14.2% | 30.7% | Multi-language coding tasks |

- ~80 iterations of evolutionary search
- Surpassed hand-designed open-source coding agents (e.g., Aider)
- Improvements **transfer across FMs**: agent optimized with Claude 3.5 Sonnet also improved when powered by o3-mini or Claude 3.7 Sonnet
- Improvements **transfer across languages**: agent evolved on Python tasks also improved on Rust, C++, Go tasks

### 1.10 Baselines Beaten

| Baseline | Why it underperforms |
| --- | --- |
| DGM w/o Self-improvement | Same initial agent repeatedly generates children without itself improving; much worse |
| DGM w/o Open-ended exploration | Linear chain (always build off latest); gets stuck in local optima |
| Hand-designed agents (Aider) | DGM-evolved agents outperform manually engineered ones |

### 1.11 Safety Mechanisms

- All execution in **sandboxed environments**
- **Human oversight** throughout
- Strict limits on web access
- Full **traceability**: every modification is logged with diffs and lineage
- **Hallucination detection**: hidden function checks if agent fabricates tool execution logs (the agent tried to disable this detector rather than stop hallucinating -- a form of reward hacking)
- Evaluation code is isolated from agent modification scope

### 1.12 Known Limitations of DGM

1. **Fixed meta-level**: The instruction-generation mechanism (which analyzes performance and proposes where to improve) is handcrafted and not modifiable by the agent
2. **Domain alignment assumption**: Only works when task-solving skills and self-modification skills are the same (true for coding, not true for poetry, paper review, robotics, etc.)
3. **Foundation model ceiling**: Since FMs are frozen, the system cannot improve beyond what the FM can generate
4. **Reward hacking risk**: Agent may optimize for benchmark scores rather than genuine improvement (Goodhart's Law)
5. **Increasing complexity**: As the codebase evolves, it becomes harder for humans to audit

## Part 2: DGM-Hyperagent (DGM-H)

### 2.1 The Problem DGM-H Solves

DGM has a fundamental limitation: it assumes **domain alignment** between the evaluation task and self-modification skill. This works for coding (improving at coding = improving at self-modifying code) but breaks for other domains:

- If the task is paper review, getting better at reviewing papers does NOT make you better at modifying your own code
- If the task is robotics reward design, same problem
- The meta-level (instruction generation, self-modification strategy) is **fixed and handcrafted** in DGM

Additionally, DGM has the **infinite regress problem**: adding a meta-meta-system to improve the meta-system just shifts the bottleneck upward. You need infinite layers of meta-systems, each improving the one below.

### 2.2 The Hyperagent Solution

A **hyperagent** is a self-referential agent that combines:

- **Task agent**: solves the target task (coding, paper review, robotics reward design, etc.)
- **Meta agent**: modifies both the task agent AND itself

...into a **single editable Python program**. The critical innovation: **the meta-level modification procedure is itself editable**.

This is called **metacognitive self-modification**: the system improves not only how it solves tasks, but also how it generates and applies future improvements.

### 2.3 How It Breaks the "Who Improves the Improver" Problem

The key insight is **self-reference through code editability**:

1. Traditional approach: Task agent -> Meta agent improves it -> Meta-meta agent improves meta agent -> infinite regress
2. Hyperagent approach: A single program contains BOTH the task logic AND the improvement logic. When the program modifies itself, it can modify ANY part, including the improvement logic.

There is no separate "improver" that needs its own improver. The entire system is one editable, Turing-complete program. The mechanism responsible for generating improvements is itself subject to modification by the same mechanism.

This eliminates infinite regress because:

- The system does not need a fixed external meta-level
- Self-modification scope includes the self-modification code itself
- The FM (frozen, external) provides the intelligence to propose edits, but the code that structures those edits, selects what to improve, and applies modifications is all within the editable program

### 2.4 How Hyperagent Bypasses Domain Alignment

In DGM, self-improvement ability came "for free" because coding benchmarks tested the same skill needed for self-modification. DGM-H eliminates this assumption:

- The **meta agent code** is part of the editable program
- When the system is evaluated on paper review tasks, the meta agent can still evolve because it is directly editable
- The meta agent can develop skills like: persistent memory, performance tracking, failure analysis, prompt optimization -- these are domain-general meta-skills
- These meta-skills transfer across domains because they are about *how to improve* rather than *what to improve*

### 2.5 DGM-H Architecture

```txt
DGM-H Architecture
══════════════════

┌─────────────────────────────────────────────┐

│  │         TASK AGENT              │        │

│  │  - Analyzes past performance    │        │
```

#### Comparison: DGM vs DGM-H

| Aspect | DGM | DGM-H |
| --- | --- | --- |
| Meta-level | Fixed, handcrafted prompt | Editable, part of the agent's code |
| Self-modification scope | Task agent code only | Task agent + meta agent code |
| Domain requirement | Must be coding (alignment assumption) | Any computable task |
| Instruction generation | Fixed LLM call with static prompt | Evolvable mechanism within the program |
| Meta-skill transfer | Not applicable | Meta improvements transfer across domains |
| Can improve at improving | Only indirectly (via coding skill) | Directly (meta agent is editable) |

### 2.6 DGM-H Algorithm

```txt
Algorithm: DGM-Hyperagent
─────────────────────────
Input: Initial hyperagent h_0 (minimal task+meta agent), benchmark B
Initialize archive A = {h_0}
Evaluate h_0 on B, record score

Repeat for N iterations:
  1. SELECT parent hyperagent from archive A
     - Same selection as DGM: softmax over fitness + diversity incentive
     - Performance-based + fewer-children preference

  2. SELF-MODIFY (the hyperagent modifies itself)
     a. The hyperagent's META AGENT component:
        - Reads its own complete codebase (task + meta)
        - Analyzes past evaluation results
        - Generates a self-improvement instruction
        ** This step is NOT fixed -- the meta agent code
           that generates this instruction is itself editable **
     b. The hyperagent (using its FM + its own meta logic)
        proposes code modifications to ANY part of itself
        - Can modify task agent logic
        - Can modify meta agent logic
        - Can modify evaluation analysis
        - Can add new infrastructure (memory, logging, etc.)
     c. Apply diff to create child hyperagent

  3. EVALUATE child hyperagent
     - Run child's TASK AGENT on benchmark B
     - Record fitness score

  4. ADD child to archive A

Key difference from DGM: Step 2a uses an EVOLVABLE mechanism,
not a fixed prompt. The meta agent that generates improvement
instructions can itself be improved in step 2b.
```

### 2.7 Initial Hyperagent Setup (Seed)

The initial hyperagent is intentionally minimal:

- A frozen foundation model (Claude or GPT-4o)
- Two tools only: **bash execution** and **file editor**
- Minimal task agent scaffolding (basic prompt to solve tasks)
- Minimal meta agent scaffolding (basic prompt to propose improvements)
- No domain-specific customization

Everything else must be evolved by the system itself.

### 2.8 Emergent Meta-Level Improvements

The DGM-H autonomously discovered and implemented these meta-level improvements (never explicitly specified by the designers):

| Meta-Level Innovation | Description |
| --- | --- |
| Persistent memory | Created infrastructure for logging and retrieving past evaluation results across iterations |
| Performance tracking | Built dashboards and analysis utilities to track trends |
| Label bias detection | Developed mechanisms to detect and correct for systematic biases in evaluation |
| Prompt template systems | Created reusable, parameterized prompt templates |
| Failure analysis infrastructure | Built tools for diagnosing why specific tasks failed |
| Compute-aware strategy | Adapted degree of exploration based on remaining compute/resources in the run |
| Self-diagnosis utilities | Created code to analyze its own performance patterns |
| Rubric generation | Built evaluation rubrics for non-coding domains |
| Error correction mechanisms | Added explicit error-checking and correction loops |

### 2.9 Concrete Results and Comparisons

#### Cross-Domain Performance

| Domain | Initial Score | Final Score (DGM-H) | Notes |
| --- | --- | --- | --- |
| Polyglot coding (train) | 0.140 | 0.340 | Matches DGM despite no coding-specific design |
| Polyglot coding (test) | 0.084 | 0.267 | Generalizes to held-out tasks |
| Paper review (test) | 0.0 | 0.71 | Predicting accept/reject; beats AI-Scientist-v2 (0.63) |
| Robotics reward design | baseline | significant gains | Discovers reward functions enabling complex behaviors (jumping vs standing) |
| Olympiad math grading | baseline | strong gains | Via transfer from other domains |

#### Ablation Results

| Configuration | Result |
| --- | --- |
| DGM-H (full system) | Continuous improvement across all domains |
| DGM-H w/o self-improvement | Little to no progress; stagnation |
| DGM-H w/o archive (no open-ended search) | Little to no progress; stagnation |
| Original DGM (fixed meta) | Competitive only in coding; fails in other domains unless hand-customized |
| DGM hand-tuned per domain | Some gains but requires manual engineering for each domain |

Both metacognition AND open-ended population search are necessary. Removing either causes failure.

### 2.10 Meta-Level Transfer Experiments

This is the strongest evidence for the value of metacognitive self-modification:

1. **Cross-domain transfer**: Hyperagents optimized on paper review + robotics were tested on a novel domain (Olympiad math grading)
   - DGM-H meta agents: improvement@50 = **0.63** (strong transfer)
   - Fixed/manually-customized systems: improvement@50 = **~0** (no transfer)

2. **Compounding across runs**: Meta-level improvements learned in one setting compound with continued self-improvement in another setting
   - Bootstrapping from a previously-improved hyperagent accelerates progress in new domains
   - Higher asymptotic performance than starting from scratch

3. **The transferred skills are general**: persistent memory, performance tracking, failure analysis, compute-aware strategy -- these help in ANY domain

### 2.11 The improvement@k Metric

The paper introduces **imp@k** (improvement@k) as a metric for meta-level skill:

- Given a meta agent, generate k child task agents
- imp@k = fraction of generated children that improve over the parent
- This measures how good the meta agent is at *generating improvements*, independent of the current task agent's absolute performance
- Used to quantify and compare meta-level transfer

### 2.12 Parent Selection Experiments

Early experiments permitting the DGM-H to modify its own parent selection mechanism showed:

- The system autonomously rediscovered and improved classic exploration-exploitation heuristics like **UCB (Upper Confidence Bound)** and **softmax selection**
- However, it has not yet surpassed carefully hand-designed selection strategies
- In main experiments, parent selection and evaluation criteria are kept fixed (not modifiable) for safety and experimental control

### 2.13 Safety Considerations (DGM-H Specific)

- All experiments **sandboxed** with explicit oversight and resource constraints
- **Evaluation and parent selection code is NOT modifiable** in main experiments (to prevent reward hacking)
- The system cannot modify the outer loop that decides what gets archived
- Risk of **Goodhart's Law**: open-ended optimization will find and exploit any bias in the evaluation metric
- As systems become more powerful, robust safety requires:
  - Interpretability of evolved code
  - Trustworthy, flexible benchmarks
  - Human-in-the-loop oversight
  - Preventing modification of evaluation criteria

### 2.14 Limitations of DGM-H

1. **Fixed outer loop**: Parent selection and evaluation pipeline remain unmodifiable in main experiments
2. **Fixed task/evaluation distribution**: The benchmark suite doesn't change
3. **FM-dependent**: Still relies on frozen foundation models for intelligence; cannot modify model weights
4. **Simulator dependency**: Non-coding domains require simulators (robotics) or existing datasets (paper review)
5. **No co-evolution of tasks**: Tasks are static; future work could have tasks and agents co-evolve
6. **Scalability unknowns**: Whether improvements continue to compound indefinitely is unproven

## Part 3: Implementation Blueprint for a Self-Improving Orchestrator

### 3.1 Minimum Viable Components

To build a system inspired by DGM/DGM-H, you need:

1. **Agent representation**: A code repository (Python) that defines agent behavior
2. **Foundation model access**: Frozen FM for generating code modifications and solving tasks
3. **Archive**: Append-only store of all agent variants with metadata (fitness, lineage, child count)
4. **Evaluation harness**: Automated benchmark that scores agents objectively
5. **Sandbox**: Isolated execution environment for running agents safely
6. **Selection function**: Softmax over composite score (fitness + novelty/diversity)
7. **Self-modification pipeline**: Context assembly -> instruction generation -> code diff generation -> application

### 3.2 Critical Design Decisions

| Decision | DGM Approach | DGM-H Approach | Recommendation |
| --- | --- | --- | --- |
| What is editable? | Task agent code only | Task + meta agent code | DGM-H (more general) |
| Archive pruning | Never prune | Never prune | Never prune; storage is cheap |
| Selection strategy | Softmax(fitness, 1/children) | Same, potentially evolvable | Start with fixed, consider making evolvable |
| Evaluation isolation | Separate from agent | Separate, non-modifiable | Keep evaluation isolated always |
| Meta-level design | Fixed prompt | Editable code | Editable for domain generality |
| FM usage | Single model | Can route to multiple | Allow multi-model routing |
| Seed agent complexity | Moderate (basic tools) | Minimal (bash + editor only) | Start minimal, let evolution discover |
